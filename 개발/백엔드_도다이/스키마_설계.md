### v1.1 (2026-07-24) — 콘텐츠 입력규격 5장 12건 반영
슈슈(리서치)가 실제 콘텐츠 1,600건을 채우며 남긴 스키마 변경 요청 12건을 반영했다. 각 건의 반영 위치와 판단은 **9장 「규격 12건 반영 대장」**에 정리했다. 요지:

- **① `content_key text unique not null`** — 전 콘텐츠 마스터 테이블에 자연키 추가. **DDL 작성 전에 반영해야 하는 최우선 항목**(테이블 만든 뒤 소급 부여는 지옥). ②~③도 동일.
- **② `source not null` · `license` · `verify`** — 전 콘텐츠 마스터에 출처·라이선스·검수 상태. 저작권 사고 시 「어느 행을 지울지」 특정 가능성의 근거.
- **③ `vocab_items.ruby jsonb`** — 단어 카드 후리가나 좌표. `reading_sentences`엔 이미 있는데 단어엔 없던 비대칭을 해소.
- **④~⑫** — 급함 표시(🔴🟠🟡)를 존중하되 **전부 반영**. `listening_lines` 자식 테이블 신설(④), `questions`/`question_choices` 루비 좌표(⑤), 자타동사·활용(⑥), `grammar_items`/`expression_items` 급수 명시(⑦), 접속형태(⑧), 단어 예문 3종(⑨), 부가뜻(⑩), 짝맞추기 키(⑪), TTS 프리셋(⑫).

> 설계 원칙과 충돌한 건은 **없었다**. 12건 모두 기존 결정(원장·단일태그·문장분리·is_published)을 건드리지 않는 컬럼/자식테이블 추가였다. 상세는 9장.

## 0. 한 줄 요약

PostgreSQL 기반 **9개 도메인 · 34개 테이블**. 설계의 축은 세 가지다.

1. **코스 종속 없는 진도 모델** — 5개 코스가 같은 테이블을 쓴다. 코스마다 테이블을 나누면 "퀵메뉴 자유 전환"(PRD 10.4)이 코스 수만큼 분기된다.
2. **우표는 잔액이 아니라 원장(ledger)** — 왜 늘고 줄었는지 설명할 수 없는 포인트는 CS 대응이 불가능하다.
3. **지문은 문장 단위로 쪼개 저장** — 해석이 토글이 아니라 "문장 탭"(PRD 8.4)이라, 통짜 텍스트로 저장하면 기능 자체가 불가능하다.

## 1. 기술 선택

### 1.1 DB — PostgreSQL (Supabase 권장)

| | 채택 | 이유 |
|---|---|---|
| **DB** | PostgreSQL | 관계형 데이터가 많다 — 태그 필터·급수 하위 필터·오답노트 다중 조건 정렬은 SQL이 압도적으로 유리 |
| **Auth** | Supabase Auth | 소셜 로그인 Must(PRD 11장). Postgres와 같은 서비스라 `auth.users` ↔ 앱 테이블을 FK로 직결 가능 |
| **Storage** | Supabase Storage | 청해 음성 · 생성된 PDF · 오프라인 촬영본 |

> ⚠️ **README 정정 필요**: 현재 `백엔드_도다이/README.md`에 "Firebase Auth · PostgreSQL"로 적혀 있다.
> Auth와 DB를 다른 벤더로 나누면 **`user_id`를 앱이 직접 동기화**해야 하고 RLS를 쓸 수 없다.
> 1인 개발에서 이건 순수한 손해라, **Auth·DB·Storage를 Supabase 하나로 통일**할 것을 제안한다.
> (Firebase를 유지해야 할 이유가 따로 있다면 알려주세요 — 6장 결정 항목 ①)

**Firebase(Firestore)를 쓰지 않는 이유**: 우표 원장 집계, "틀린 횟수 많은 순 정렬", "태그+급수+영역 3중 필터"(화면 47)가 전부 NoSQL에서 비싸진다. 게임화 수치가 많은 앱이라 집계 쿼리가 계속 늘어난다.

### 1.2 로컬 DB — SQLite (expo-sqlite)

오프라인 ①열람 ②촬영(PRD 5.6)은 **서버 없이 동작해야** 하므로, 아래는 로컬에 미러링한다.
자세한 동기화 규칙은 5장.

### 1.3 설정값은 전부 config

PRD 수치(우표 7/5/10개, 월 3회, 세션 분량 10/5/1/3, 구독가)는 **코드·스키마에 하드코딩하지 않고** `app_configs` 테이블 + 서버 설정으로 뺀다. 밸런스는 출시 후 반드시 조정된다.

### ② 콘텐츠 마스터

> 🆕v1.1 **전 콘텐츠 마스터 테이블 공통 컬럼** (규격 5장 ①②) — `vocab_items` · `expression_items` · `grammar_items` · `listening_items` · `reading_texts` · `reading_sentences`(reading은 text 종속) · `tips` · `questions` · `question_choices`(choice는 question 종속)에 아래를 **전부** 붙인다. DDL에서는 `content_master_cols` 패턴으로 반복.
>
> | 컬럼 | 타입 | 설명 |
> |---|---|---|
> | `content_key` | text **unique not null** | 사람이 읽는 안정 키 `{코스}.{급수}.{종류}.{4자리}` 예 `jlpt.n5.vocab.0001`. **음성 파일명·재임포트(UPSERT)·오류보고**의 근거. uuid는 임포트 후에 생기므로 자연키가 없으면 이 셋이 전부 막힌다(규격 4.0) |
> | `source` | text **not null** | `own`/`jlpt_official`/`aozora:{id}`/`tanos_ccby`/`ref_only:{출처}` 등. 빈칸이면 임포트 거절 |
> | `license` | text null | 출처가 라이선스를 요구할 때(예 `CC BY`). `own`이면 null |
> | `verify` | text **not null** | `draft`/`team`/`native`. 출시 게이트는 코스별로 다름(규격 1.3) |
> | `is_published` | bool **not null default false** | 🔴 **미공개 ≠ 잠금**. false면 목록·셀렉터·검색 어디에도 안 나옴. `is_locked`는 만들지 않음 |
>
> 🔴 **①②③은 DDL 작성 「전에」 반영**했다 — 테이블 만든 뒤 자연키를 소급하면 이미 들어간 행에 키를 뒤늦게 부여해야 하고, 그 순간 UPSERT 기준이 없어 중복이 쌓인다(규격 5장 서문).

> ⚠️ **「우리가 아직 안 만든 것」에만 쓴다.** 만들어 놓고 조건부로 여는 데 쓰면 **이름만 바꾼 잠금**이 된다. `course_tracks` 에도 동일 컬럼.
> `vocab_goal_count`는 대략치이며 추후 일본인 검증 후 수정 예정(JLPT 검토 ③-A).

> ⭐ `outcome`에 `skipped`가 따로 있는 이유: **"틀림(✕)"과 "넘어감(⤼)"은 성격이 다르다**(JLPT 검토 ⑦-3). 오답노트에서 시각적으로 구분해야 하므로 bool로 뭉개면 안 된다.

| 컬럼 | 설명 |
|---|---|
| 🔗 `user_id`, `course_level_id`, `track_id` | (unique) |
| `cycle_no` | **N회독째** |
| `items_done` / `items_total` | 현재 회독 진척 |
| `cycle_wrong_rate` | 이번 회독 오답률 |
| `prev_cycle_wrong_rate` | **직전 회독 오답률** |

> ⭐ `prev_cycle_wrong_rate`를 남기는 이유: 회독 모델의 목적은 진도가 아니라 **"거듭할수록 오답률이 줄어드는 걸 보여주는 것"**(JLPT 검토 ③-B). 직전 값이 없으면 그 화면을 만들 수 없다.

#### `reading_progress` — "N회 읽음"
`user_id` / `reading_text_id` / `read_count` / `last_read_at` / `quiz_taken_count`

> ⭐ **프로그레스바가 아니라 카운터인 이유**: 뉴스는 콘텐츠가 무한이라 분모가 없고, 읽기는 "끝냈다"가 무의미하다. 프로그레스바는 "빨리 채워라" 신호라 철학과 충돌(코스별 검토 1번).

> `quiz_taken_count`가 별도인 이유: 이해 퀴즈는 **선택**이라 회독과 분리해야 한다.

> 🔴 **`delta`가 양수인 소비처는 없다.** 우표는 **결제로 구매 불가**(PRD 11장 Won't) — `reason`에 `purchase`를 아예 정의하지 않는 것으로 규칙을 스키마에 새긴다.

#### `stamp_balances` — 읽기 캐시
`user_id` / `balance` / `last_ledger_id`. 홈·요약 화면에서 매번 SUM 하지 않기 위한 캐시일 뿐, **진실은 언제나 원장**이다.

#### `exports` — PDF 발행 기록
| 컬럼 | 설명 |
|---|---|
| `export_type` | `daily_summary`(오늘의 편지) / `wrong_note` / `vocab_book` / `reading` |
| `stamp_cost` | 7 / 5 / 10 / 0 |
| `counts_to_monthly_quota` | bool — 단어장·독해만 true |
| `file_url` | Storage 경로 |
| `furigana_on` / `romaji_on` | ⭐ **발행 시점 토글 캡처** |
| `content_snapshot` | jsonb — 발행 시점 학습 내용 |
| `filter_snapshot` | jsonb — 단어장 PDF의 태그 필터 상태 |

> 🔴 **토글 상태를 캡처하는 이유**: 이미 받은 PDF는 이후 설정을 바꿔도 그대로여야 한다(PRD 8.4).
> 🔴 **`content_snapshot`에 진행률·회독·D-day·우표를 넣지 않는다**(PRD 8.2.1). 종이에서 무의미하고 인쇄 시점 값이 박제되어 혼란을 준다. **대표님이 특히 강조한 항목**이라 스키마 주석에도 명시할 것.

#### `export_quotas` — 월 할당량
`user_id` / `year_month` / `export_type` / `free_used`(월 3회) / `stamp_extra_used`(⭐ **월 최대 2회 상한**)

> `stamp_extra_used`를 따로 세는 이유: 단어장 PDF는 "무료 3회 + 우표 10개로 추가, **단 월 +2회까지**"라 상한이 구독 가치를 보호한다(PRD 12.1). 원장만으로는 이 상한을 판정할 수 없다.

### ⑧ 기록 · 리워드

#### `daily_summaries` — 오늘의 학습 요약 = 편지함
`user_id` / `study_date` / `learned_vocab_ids` jsonb / `wrong_question_ids` jsonb / `advice_text` / `course_extra` jsonb

> ⭐ PRD 8.3의 "편지함"은 **이 테이블을 그대로 재사용**한다. PDF 생성용으로 어차피 저장되는 데이터라 신규 저장이 없다 — 구현 비용이 거의 0인 이유.
> `course_extra`에 JLPT의 회독·진행률 변화, D-day가 들어간다. **화면에만 쓰고 PDF에는 넣지 않는다**(8.2.1).
> `advice_text`는 규칙 기반으로 생성(오답이 몰린 카테고리, "안다고 했는데 틀린 단어 N개"). MVP에 AI 불필요.

#### `tomo_notes` / `user_tomo_notes`
토모의 쪽지 — `ja` / `ko` / `context_tag`. 사용자별로 본 쪽지 기록.
> **보상·우표와 연결하지 않는다**(PRD 14.5 — 보기 전용). 그래서 `stamp_ledger`에 이 reason이 없다.

### ⑨ 구독 · 오프라인

#### `subscriptions`
`user_id` / `plan`(`trial`/`free`/`monthly`/`yearly`) / `status` / `trial_ends_at` / `current_period_end` / `store`(`apple`/`google`) / `original_transaction_id`

> **D1~D7 프리미엄 체험 → D8 자동 무료 전환**(PRD 12장). 결제 실패로 인한 강제 이탈이 없도록 `free`가 항상 유효한 종착 상태다.

#### `offline_captures` — 오프라인 촬영 대기열
`user_id` / `local_path` / `remote_path` / `captured_at` / `status`(`pending`→`uploaded`→`ocr_done`) / `ocr_result` jsonb / `notified` bool

> ⭐ **로컬이 원본, 서버가 사본**이다. 오프라인에서 찍히므로 서버 행이 나중에 생긴다.
> ⭐ `notified`를 두되 **기본은 알리지 않는다** — 온라인 복귀 시 "조용히 자동 OCR 처리"가 결정 사항(PRD 5.5, 토모의 과묵한 톤).
> ⭐ 무료·구독 **모두 허용**. 여기서 막으면 5.5의 의미가 없다(PRD 5.6 ②).

#### `content_downloads` — 콘텐츠 미리 받기 (구독 전용)
`user_id` / `scope_type` / `scope_id` / `downloaded_at` / `expires_at` / `bytes`

> ⭐ **여기만 구독 체크가 붙는다**(PRD 5.6 ③). ①열람·②촬영에는 구독 검사를 넣지 않는다 — 이미 내 기기에 있는 걸 오프라인에서 보는 건 기능이 아니라 당연한 동작이고, 막으면 오히려 버그다.

### 6.1 오프라인 우표 — 조작 방지 설계

> 🔴 **대전제: 막지 말고 미룬다.** 검증에 실패해도 **학습 기록은 항상 반영**한다.
> 우표만 보류할 뿐 학습을 무효로 만들지 않는다 — 그건 PRD 1.3 철학을 정면으로 어긴다.

**핵심 구조 — 로컬은 잔액을 못 만진다**

```
[오프라인]  학습 로그를 로컬 큐에 쌓음 → 화면엔 "우표 1장 · 연결되면 도착해요"
[온라인]    큐 업로드 → 🔒 서버가 검증 → 서버가 stamp_ledger 발급 → 도착 알림
```

`stamp_ledger`는 **서버 전용 쓰기**다. 앱은 어떤 경로로도 원장에 직접 쓰지 못한다(RLS `insert` 차단, 서버 함수로만 발급). 이 한 줄이 조작 방지의 8할이다.

**검증 규칙 5가지**

| # | 규칙 | 막는 것 | 왜 사용자에게 부담이 없나 |
|---|---|---|---|
| 1 | **미리 받은 범위 안의 콘텐츠만 인정** (`content_downloads`에 없으면 거절) | 존재하지 않는 레슨을 풀었다고 조작 | 안 받은 걸 오프라인에서 풀 수는 없다 — 물리적으로 당연 |
| 2 | **날짜는 서버 시간 기준.** 로그엔 `device_time` + `monotonic_ms`(부팅 후 경과, 시계 조작과 무관)를 함께 담아 대조 | 폰 시계를 돌려 하루치를 여러 번 | 정상 사용자는 두 값이 자연스럽게 일치 |
| 3 | **하루 상한 = 우표 1장** (오늘의 학습 1단위) | 반복 제출로 대량 적립 | **온라인과 완전히 같은 규칙** — 오프라인에만 거는 제약이 아니다 |
| 4 | **세션 최소 소요 시간 미달 시 보류** (예: 10단어를 5초) | 자동화·스킵 | 거절이 아니라 **보류**. 토모 톤으로 "다시 한 번 볼까요?" |
| 5 | **소급 인정은 최대 7일** | 오래된 로그 대량 투입 | 여행 최대 기간을 커버. 초과분도 **학습 기록은 반영**되고 우표만 미지급 |

**필요한 스키마 변경**

`study_sessions`에 아래 컬럼 추가:
| 컬럼 | 설명 |
|---|---|
| `is_offline` | bool |
| `device_time` | timestamptz — 기기가 주장하는 시각 |
| `monotonic_ms` | bigint — 부팅 후 경과 시간 (시계 조작 불가) |
| `synced_at` | timestamptz null |
| `verify_status` | `pending` / `verified` / `held`(보류) |

`stamp_ledger.reason`에 값 추가: **`daily_study_offline`**
→ 원장에서 오프라인 적립분을 분리 집계할 수 있어야 한다. 밸런스가 이상하면 여기부터 본다.

> ⭐ **UX로 새는 곳**: 오프라인 학습 중 화면엔 우표가 **"도착 예정"** 으로 보인다(신규 19-b 화면).
> 이미 받은 것처럼 보였다가 나중에 회수하면 사용자는 배신감을 느낀다 — **처음부터 "예정"이라고 말하는 게 유일하게 정직한 방법**이다.

## 9. 규격 12건 반영 대장 (v1.1)

규격 `콘텐츠_입력규격.md` 5장의 스키마 변경 요청 12건 전부의 반영 결과다.

| # | 대상 | 요청 | 반영 위치 | 설계 충돌 여부 | 급함 |
|---|---|---|---|---|---|
| ① | 전 콘텐츠 마스터 | `content_key text unique not null` | ② 공통컬럼 · `schema.sql` `content_master_cols` | 없음 (신규 컬럼) | 🔴 |
| ② | 전 콘텐츠 마스터 | `source not null` · `license` · `verify` | ② 공통컬럼 · `schema.sql` | 없음 | 🔴 |
| ③ | `vocab_items` | `ruby jsonb` | `vocab_items` 정의 · DDL 완성 · 임포터가 생성 | 없음. `reading_sentences`와 대칭이 됨 | 🔴 |
| ④ | `listening_items` | 대본을 자식 테이블 `listening_lines`로 | `listening_lines` 신설. `script_ja/ko` 폐기 | 없음. `reading_sentences` 패턴 재사용 | 🟠 |
| ⑤ | `questions`·`question_choices` | 각각 `ruby jsonb`(`stem_ruby`·`choice_ruby`) | ③ 문제·퀴즈 정의 | 없음 | 🟠 |
| ⑥ | `vocab_items` | `conj_type`·`transitivity` | `vocab_items` 정의 · DDL | 없음 | 🟠 |
| ⑦ | `grammar_items`·`expression_items` | `course_level_id` 명시 | 두 테이블 정의에 🔗추가 | **누락 수정** — 설계 필드목록에서 빠져 있던 것을 채움 | 🟠 |
| ⑧ | `grammar_items` | `connection`(접속형태) | `grammar_items` 정의 | 없음 | 🟠 |
| ⑨ | `vocab_items` | `example_ja`·`example_ruby`·`example_ko` | `vocab_items` 정의 · DDL | 없음. grammar와 대칭 | 🟡 |

| ⑪ | `question_choices` | `pair_key` | `question_choices` 정의 | 없음 | 🟡 |
| ⑫ | `listening_items` | `voice_preset`·`speed` | `listening_items` 정의 | 없음 | 🟡 |

**판단 기록**
- **설계와 정면충돌한 건은 0건이다.** 12건 모두 (a)신규 컬럼 추가이거나 (b)통짜→자식테이블 분리(④)이거나 (c)설계 누락 수정(⑦)이라, 기존 핵심 결정(우표 원장·단일 태그 FK·문장 단위 분리·`is_published`≠`is_locked`)을 하나도 뒤집지 않았다.
- **⑦은 「변경」이 아니라 「누락 수정」**으로 분류했다. 설계 v1.0의 `grammar_items`/`expression_items` 필드 나열에서 `course_level_id`가 실수로 빠져 있었고, 다른 아이템 테이블(`vocab_items`·`reading_texts`)은 이미 급수 FK를 갖고 있었다. 즉 규격이 옳고 설계 서술이 틀렸던 것.
- **④는 「폐기+신설」**: 원 설계의 `listening_items.script_ja/script_ko`(통짜 텍스트)를 버리고 `listening_lines` 자식 테이블로 옮겼다. 근거는 규격 4.4 — 회화형 청해는 화자 분리가 필수인데 통짜 텍스트로는 불가능. `reading_texts`→`reading_sentences`와 완전히 같은 1:N 분리라 설계 철학과 오히려 일관된다.

**남은 리스크 (나머지 콘텐츠가 이 스키마로 들어가는가)**
- 🟢 **문법·표현** — `vocab_items`와 같은 CSV·같은 공통컬럼·같은 루비 규칙. `import_vocab.py`의 매핑 로직을 컬럼명만 바꿔 재사용 가능. 낮은 리스크.
- 🟡 **청해** — 대본이 별도 JSON(발화 단위)이라 임포터를 새로 써야 한다. 스키마(`listening_lines`)는 준비됨. 루비 좌표 변환 로직은 공유.
- 🟡 **지문** — JSON 1:N. `reading_sentences`에 문장별 `ruby jsonb` 생성 필요. 60자 초과 검수 경고(규격 6.1-11)를 임포터에 넣어야 함.
- 🟠 **문항** — 6종 유형별 필수필드가 달라(규격 4.6) 유형별 검증 분기가 필요. `matching`의 `pair_key`, `speaking`의 choices-없음 등. 스키마는 준비됨(⑤⑪ 반영). 임포터 복잡도만 높다.
- 🔴 **공통 미해결**: `romaji_ko` 역생성 검증(규격 6.1-6)의 기준 구현이 현재 Python(`kana_to_ko.py`)이다. FE(무스부)가 TS로 포팅할 때 **`WORD_EXCEPTIONS`를 코드가 아니라 데이터로** 들고 가야 한다(규격 3.2.6-1). 안 그러면 급수마다 재수정.
