01 테마 시스템

모든 색은 light / dark 두 값을 쌍으로 갖는다. 컴포넌트는 원시 hex를 직접 쓰지 않고 토큰만 참조한다.

설정 — 화면 표시 (35번 화면)
표면 계층 (surface / elevated)

bg-surface

카드·시트. border 1px으로 배경과 분리.

bg-elevated

모달·팝업. 라이트에서는 색이 아니라 그림자로 띄운다.

MEMO 라이트 배경이 순백이 아니라 따뜻한 오프화이트 #FAF7F3 인 이유 — 순백은 장시간 응시 시 눈이 피로하고, 앰버 브랜드와 색온도가 어긋난다. 라이트에서 bg-surface와 bg-elevated는 동일한 #FFFFFF이며 그림자로만 구별된다. 다크에서는 색상값 자체가 달라진다(#1E1A17 / #2A2521).

2.3 코스 5색 — 면

MEMO 브랜드가 앰버이므로 주황·노랑 계열은 배제한다. 코스색은 태그·카드 테두리·진행바에만 쓰고 대면적 배경은 금지. 이 색이 PRD 14.2의 "코스 구분은 캐릭터가 아니라 컬러·태그로"를 담당한다 — 이 색을 없애면 코스 구분 장치가 사라진다.

확정 — 2026-07-21 브랜드에서 brand(면) / brand-text(글자)를 나눈 것과 똑같은 패턴을 코스색에도 적용한다. 토큰이 5개 늘지만 디자인 시스템에서는 패턴 일관성이 개수보다 우선이다 — 규칙이 하나면 실수도 하나만 막으면 된다.
· 면(태그 배경·테두리·도트·진행바 채움) = course-*  /  글자(라벨·아이콘) = course-*-text
· 라이트 값은 원색의 색상(hue)·채도를 유지하고 명도만 낮춰 bg-base #FAF7F3·bg-surface #FFFFFF 두 표면 모두 4.5:1 이상이 되도록 실측해 정했다.
· JLPT(4.57)·비즈니스(6.01)는 원색이 이미 통과하므로 값을 바꾸지 않았다. 토큰만 정의해 5색 전부 같은 방식으로 참조되게 한다.
· 다크는 기존 값이 이미 전부 통과 → course-*-text = 코스색 동일. 브랜드와 완전히 같은 구조다.

2.4 상태색

MEMO 오답색은 의도적으로 채도를 낮춘 톤이다. 강한 빨강은 죄책감을 유발해 PRD 14.4 관찰자 톤·1.3 철학과 충돌한다. 상태색은 배지·재촉 장치로 쓰지 않는다(설계 원칙 3 — 압박 장치 없음).

2.5 상태색 틴트 규칙 신설 · 2026-07-22

상태색을 자기 색으로 틴트한 배경 위 「작은 글자」에 그 상태색을 쓰지 않는다. 상태색은 아이콘 · 큰 글리프 · 테두리에만 쓰고, 그 위 본문은 text-high / text-mid 로 쓴다.

발견 경위 — Hi-fi 17번 error(#B5533D)는 bg-base 위에서 4.61:1로 AA를 통과한다. 그런데 같은 색으로 12% 틴트한 배경 위에 얹으면 배경이 함께 붉게·밝아져 3.93:1로 떨어진다.
왜 놓치기 쉬운가: 토큰 표는 색을 bg-base·bg-surface 기준으로만 검증한다. 틴트 배경은 표에 없는 제3의 표면이라 검증 범위 밖으로 새어 나간다 — 그래서 “토큰을 썼으니 괜찮다”는 잘못된 안심이 생긴다.
이건 error만의 문제가 아니다. success·info·코스 5색·brand 등 자기 색으로 틴트한 배경을 만드는 모든 색에 적용된다 — 기본 태그가 이미 코스색 12% 배경을 쓴다.
🔴 이 페이지 자신도 이 규칙을 어기고 있었다. 접근성 표의 .pill.pass/.warn이 상태색 틴트 배경 위 11px 상태색 글자였다. 지금은 테두리 + 앞 글리프(● / ▲)가 상태를 전달하고 글자는 text-high다 — 색을 빼도 뜻이 읽힌다.

on-brand 가 모드 무관인 이유 규칙이 아니라 사실에서 나온다 — brand 자체가 라이트/다크 동일값(#F5B942)이므로, 그 위에 얹는 글자만 모드에 따라 바뀌면 오히려 대비가 깨진다. 다크에서 밝은 글자로 바꾸면 1.17:1로 사실상 안 보인다.
값은 라이트 text-high와 같다 — 새 색을 만든 것이 아니라 「고정 대응색」에 이름을 붙인 것이다. 순수 검정(#000, 11.90:1)도 통과하지만 쓰지 않는다: 앰버는 따뜻한 색이라 중성 검정을 얹으면 색온도가 어긋나고, 이미 있는 값을 재사용하면 토큰이 늘지 않는다.
scrim 상세와 다크의 한계는 04장 「모달 · 바텀시트」 문서 블록 참조.

3.1 한·일 한자 자형 차이 필수

✓ lang="ja" + 일본어 폰트 스택 강제

주의 直·骨·次·海·器 등은 한국(강희자전 계열) 자형과 일본 신자체 자형이 다르다. 예: 直의 세로획이 아래에서 꺾이는 위치, 骨 윗부분의 꺾임 방향, 海의 안쪽 점 개수. 일본어 학습 앱에서 일본어가 한국식 자형으로 렌더되면 틀린 글자를 가르치는 셈이다. ⚠️ 이 페이지의 위 두 칸은 시스템 폰트에 의존한다 — 보는 기기에 일본어 폰트가 없으면 둘 다 폴백되어 차이가 안 보인다. 차이를 실제로 확인하려면 font_verification.html 을 보라 — 폰트를 번들해 190px로 렌더하고 차이 나는 획에 링을 얹어 지목한다.
✅ 폰트 확정 — 2026-07-22 일본어 폰트는 2개가 상한이다(1웨이트당 1~2MB, 서브셋팅 불가 — 내일 어떤 한자가 나올지 오늘 알 수 없다).
· 한국어 UI = Pretendard (1.48MB)  /  일본어 본문 = Noto Sans JP (2.18MB)  /  일본어 정서 = Zen Maru Gothic (2.79MB)  → 합계 6.45MB
· 웨이트는 Regular 400 + SemiBold 600 2종만. (예외: Zen Maru Gothic 은 600이 배포되지 않아 700)
❌ Pretendard JP 탈락 — 骨·海 등 7글자 전부 한국식 자형이었다. 가나만 일본식이라 화면은 “일본어답게” 보이는데 자형은 틀린 상태가 된다 — 틀렸다는 사실 자체가 감춰지므로 전부 틀린 것보다 위험하다. 게다가 3.92MB로 Pretendard + Noto Sans JP(3.66MB)보다 크다.
❌ Noto Serif JP 탈락 — Zen Maru Gothic 이 정서용 자리를 대체한다. 토모가 둥근 등불이라 조형이 맞고, 전래동화 주력이 N5~N4 리라이트본이라 명조의 격식이 필요 없다.

근거 — 조판 관행 신문·출판이 “숫자와 단위”, “이름과 직함” 을 붙여 두는 것과 같은 기법이다. 의미상 한 덩어리인 것은 조판에서도 쪼개지 않는다. ⋯ 는 장식이 아니라 그 문장에 속한 컨트롤이므로, 떨어지면 오작동을 유발하는 배치가 된다.
⚠️ 묶는 범위는 어절 하나까지. 문장 전체를 nowrap 으로 감싸면 문장이 화면 밖으로 나간다. 그 대가로 앞 줄이 조금 짧아 보일 수 있는데, 컨트롤이 엉뚱한 줄에 앉는 것보다 낫다.
→ 함께 필요한 것: 지문 문장 길이 가이드 (320px에서 일본어 16자 초과 시 줄바꿈 발생).

왜 토글을 나눴나 — PRD 8.4 개정 두 도구의 수명이 다르기 때문이다. 후리가나는 N2까지 쓰는 도구지만, 한글 발음은 빨리 떼야 하는 보조바퀴다 — つ·ざ·ん 같은 소리는 한글로 정확히 적을 수 없어서, 계속 의존하면 틀린 발음이 굳는다.
묶어 두면 발음을 떼려는 순간 후리가나까지 사라진다. 초급을 막 벗어나는 사용자 — 정확히 이 앱이 키우려는 사용자 — 에게 "둘 다 쓰거나 둘 다 버리거나"라는 잘못된 선택을 강요하게 된다. 그래서 나눴다.
구현 규칙 — 처리가 서로 다르다 루비 크기 = 본문의 50%(18 → 9). 두 토글은 같은 컴포넌트지만 레이아웃 처리가 반대다.
· 후리가나 = 공간 항상 확보 (line-height 최소 2.0 + visibility:hidden). 읽는 도중에 자주 누르는 토글이라, 켤 때마다 글이 밀리면 읽던 자리를 잃는다.
· 한글 발음 = 공간 회수 (display:none, 루비와 겹치지 않는 별도 줄). 학습 단계가 바뀔 때 한 번 끄면 계속 끄는 사실상의 설정이다. 안 쓰는 사용자가 빈 줄을 영원히 볼 이유가 없고, 세로 공간은 지문에 쓰는 편이 낫다.
🔴 판별 기준(사양서 4.1): "읽는 중 자주 토글하는가?" — 그렇다면 자리 고정, 아니라면 회수 가능. 레이아웃 점프 방지는 목적이 아니라 수단이다. 자주 안 바뀌는 것까지 자리를 잡아두면 화면만 낭비한다.
기본값: 온보딩 Q2(현재 수준) 연동 — 완전 초보 = 둘 다 ON / 조금 안다 이상 = 후리가나만 ON. 단, PRD 8.4 통합 원칙에 따라 학습 카드 앞면·읽기형 지문 첫 노출은 설정과 무관하게 기본 OFF로 시작한다.

04 컴포넌트 — 5블록 문서화

사양서 4.7 문서화 형식에 따라 모든 컴포넌트를 원칙 → 사용 가능한 속성 → 대표 예시 → ✅ → ❌ 다섯 블록으로 기술한다. 모든 터치 타깃은 최소 44×44.

왜 ❌ 블록을 넣는가 금지 예시가 가장 강력한 문서다. “이렇게 쓰세요”는 읽고 넘기지만 “이건 실제로 이렇게 망가졌다”는 기억에 남는다. 아래 ❌ 는 상상이 아니라 우리가 이 프로젝트에서 실제로 낸 실수거나, 검증 중 수치로 미달이 확인된 것만 적었다. 숫자가 붙어 있으면 실측값이다.

07 토모 밝아짐 — 모드별 표현이 다르다

"새 쪽지가 있으면 토모가 밝아진다"(PRD 14.5)는 어두운 배경에서만 강력하다. 밝은 배경에선 빛이 잘 보이지 않는다. 아래 4칸은 페이지 테마와 무관하게 각 모드의 실제 색을 고정 렌더해 나란히 비교한다.

MEMO 배지·빨간 점을 쓰지 않는다는 원칙은 두 모드 모두 유지하고, 라이트에서는 밝기 대신 크기·헤일로로 신호를 만든다. 토모는 단일 고정 캐릭터이며 성장하거나 완성되지 않는다(PRD 14.2). 상황별 변화는 소품을 드는 것이 아니라 비추는 대상이 바뀌는 것.
여기 도형은 전부 placeholder다 — 실제 일러스트는 별도 트랙이며, 이 페이지에서는 밝아짐 신호의 크기·강도만 판단하면 된다.
확정 — 2026-07-21 · 레이아웃 규칙 홈 화면의 토모 자리는 1.15배 기준으로 잡고, 평소(1.0배)에는 그 안에서 작게 놓인다. 즉 확대분 여백(약 12%)을 항상 비워둔다 — 토모가 커질 때 주변 요소가 밀리지 않는다.
🔴 이것은 3.2 후리가나 규칙과 정확히 같은 원리다. 후리가나도 "루비 공간을 항상 확보해두고 표시 여부만 바꾼다"였다. 여기서도 "최대 크기 공간을 항상 확보해두고 크기만 바꾼다". 토모리의 레이아웃 원칙 = 상태가 바뀌어도 자리는 바뀌지 않는다. 두 사례가 같은 규칙의 두 적용이므로, 앞으로 가변 요소는 전부 최대 크기로 자리를 잡는다.
확대는 상태 전이가 아니라 지속 상태다 — 250ms·ease-out 규칙은 "확대되는 순간"에만 적용되고, 확대된 채로 머무는 동안에는 어떤 애니메이션도 돌지 않는다(맥동·펄스 금지).
위 4칸에서 LIGHT 평소 / LIGHT 새 쪽지 두 칸의 칸 높이가 동일한 것이 이 규칙이 지켜진 상태다.
