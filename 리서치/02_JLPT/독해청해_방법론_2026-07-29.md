# JLPT 독해·청해 — 제작 방법론 (v1.0)

> 작성 2026-07-29 · 담당 슈슈(리서치) · 문법 방법론(`문법_방법론_2026-07-28.md`) 3단 구조를 **지문·문항형에 맞게 변형**
> 상위 맥락: `기획/진행상태.md`(2-c 병렬 트랙) · 규격 `리서치/콘텐츠_입력규격.md` 4.4/4.5/4.6 · 청해 음성 `리서치/청해_음성_제작_검토.md`
> 짝 산출물: `N5_독해_파일럿.csv` · `N5_청해_파일럿.csv` (이 방법론으로 실제 3건씩 채운 결과)

## 0. 이 문서가 하는 일
독해(`reading_texts`+`reading_sentences`+`questions`)·청해(`listening_items`+`listening_lines`+`questions`) 콘텐츠를 **무엇을 어떤 틀로(유형) 어떻게 짓는지(자작)** 정한다.
FE 본편 JLPT 허브의 "독해"·"청해" 영역을 켜려면 이 방법론으로 급수별 지문·대본을 채워야 한다. **단어·문법이 먼저 깔린 뒤 착수**한다 — 지문/대본이 그 어휘·문법을 재료로 쓰기 때문이다.

## 1. 🔴 문법과의 결정적 차이 — 순위도 표준 목록도 없다. **본체가 창작이다**
- 단어는 ①범위 ②빈도 순위 ③교차검증의 3단, 문법은 **급수 표준 세트 전량**이었다.
- 독해·청해는 **둘 다 아니다.** "N5 독해에 어떤 지문을 넣나"라는 정답 목록이 존재하지 않는다. 시중 문제집의 지문·대본을 쓰면 **명백한 어문저작물 복제**다(규격 1.1).
- 그래서 이 트랙의 본체는 **전량 자작 창작**이다. 방법론이 정하는 것은 "무엇을 베껴 오나"가 아니라 **"공식 문항 *유형*이라는 골격 안에서, 급수 어휘·문법이라는 재료로, 어떻게 안전하게 지어내나"**이다.
- ⚠️ 그래서 검증 부담이 단어·문법보다 크다. 단어는 뜻 1개가 맞나 틀리나지만, 지문은 **자연스러움·일관성·급수 초과 여부**를 문장마다 봐야 한다.

## 2. 방법론 (유형 골격 → 자작 → 재료 제약 → 검증)

### ① 유형 골격 — 공식 문항 "유형"만 차용 (규격 4.6 준수)
- JLPT 공식(jlpt.jp) 문항 **유형**(과제이해·포인트이해 등)을 **골격으로만** 쓴다. 원문 지문·대본·선택지는 **한 글자도 복제하지 않는다**.
- 근거: 문항 유형(예: "짧은 대화를 듣고 무엇을 해야 하는지 고른다")은 **아이디어·형식**이지 저작 표현이 아니다. 문법의 Tanos 골격, N1 단어의 코퍼스 골격과 같은 논리 — **골격은 안전, 값은 자작**.

### ② 자작 — 지문·대본·문항·해설 전량 `source=own`
- 지문(passage)·대본(script)·문항(question)·선택지(choice)·해설(explanation) **전부 우리가 쓴다**. 유형만 참고했으면 `source=ref_only:jlpt_official`, 완전 창작이면 `source=own`.

### ③ 재료 제약 — 해당 급수 이하 어휘·문법만 (본 방법론의 핵심)
- 지문·대본은 **해당 급수 이하의 단어 + 해당 급수 이하의 문법만**으로 짓는다(N5면 N5 단어세트 + `N5_문법_스코프_2026-07-28.md`의 48항목 범위).
- 이유: ① 학습자가 지문 자체는 읽을 수 있어야 한다(모르는 상위 단어가 섞이면 독해가 아니라 단어에서 막힌다) ② 문법 예문 제약(4.1)과 일관 — **"그 급수의 재료로만 짓는다"**가 단어→문법→독해·청해로 이어지는 하나의 원칙이다.
- 불가피한 상위 단어(예: 고유명사·필수 소도구)는 후리가나+해석으로 보조하되, **검수 기계가 지문 형태소를 vocab 세트와 대조해 초과 어휘를 후보로 보고**(사람 판정 — 단어 3.2.5-2와 같은 방식).

### ④ 교차검증 — 공식 샘플 유형 + 팀 + native 순차
- Tanos 같은 표준 목록이 없으므로, 검증은 **유형 적합성(공식 샘플 대조)** + **자연스러움·급수 준수(기계+팀)**로 한다.
- `verify=team`으로 출시, `native`는 출시 후 순차(단어·문법과 동일). ⚠️ 단 청해 대본의 **자연스러운 회화감**은 기계가 못 잡으니 native 우선순위를 문법보다 앞에 둘지 판단 필요(11장).

## 3. 🔴 저작권 (규격 1장 준수)
| 자리 | 값/원칙 |
|---|---|
| **문항 유형(골격)** | 공식 유형 참고 — `source`가 아니라 유형 참고 시 `ref_only:jlpt_official` |
| **지문·대본·문항·선택지·해설** | **전량 자작** → `source=own` |
| 공식 샘플 원문 | **복제 절대 금지** — 지문/대본/선택지 문장을 옮기면 즉시 어문저작물 침해 |
| 시중 문제집 | 지문·대본·해설·선택지 배열 전부 복제 금지 |

> 독해·청해는 프로젝트에서 **저작권 리스크가 가장 큰 트랙**이다(문항은 그 자체가 저작물). 그래서 "유형만, 값은 전량 자작"을 한 줄도 예외 없이 지킨다.

## 4. 🔴 어휘·문법 제약 규칙 (검수 기계가 강제)
- 지문/대본의 모든 형태소는 **≤해당 급수 vocab 세트**에 있어야 한다. 초과 시 검수 경고 → 사람 판정.
- 문법 패턴은 **≤해당 급수 문법 스코프**(N5는 48항목)만. 상위 문형 사용 금지.
- 급수 표시 분모는 단어·문법과 동일하게 **"우리 앱에 실린 수"**(외부 추정치 비노출).

## 5. 문항 유형 정의 (자작 시 이 골격을 따른다)

### 독해 (reading)
| 유형 | 성격 | N5 형태 |
|---|---|---|
| **내용이해(단문)** | 짧은 글의 사실·주제 파악 | 일기·메모 60~120자 + 객관식 1문 |
| **내용이해(중문)** | 조금 긴 글의 이유·심정 | (N5는 얕게, N4부터 본격) |
| **정보검색** | 안내문·게시에서 조건 맞는 정보 찾기 | 안내문·시간표 + "몇 시부터?" 류 1문 |

### 청해 (listening)
| 유형 | 성격 | N5 형태 |
|---|---|---|
| **과제이해(課題理解)** | 대화 뒤 **무엇을 해야 하나** | 짧은 대화 3턴 + "무엇을 가져가나?" |
| **포인트이해(ポイント理解)** | 특정 포인트(시각·이유·장소) | 짧은 대화 + "몇 시에 만나나?" |
| **발화표현(発話表現)** | 그림 상황에 맞는 말 고르기 | 🔴 **그림 asset 필요** → 파일럿 제외(11장 판단대기) |
| **즉시응답(即時応答)** | 한 마디 듣고 **가장 알맞은 응답** | A 1줄 + 응답 후보 3~4개 |

## 6. 표기 규칙 (규격 3장 준수)
- **루비**: 한자에 `{漢字|よみ}` 브래킷(규격 3.1). 한자 없으면 그대로. 지문·대본·문항·선택지 **모든 일본어 필드**에 루비.
- **한글 발음(romaji_ko)**: **기계 생성 규칙 A안 = 청음=격음 고정**(규격 3.2.2), 촉음·발음·장음·조사 예외는 규격 3.2.3~3.2.6-1. **값은 사람이 안 적는다** — build 기계가 루비에서 채운다. 파일럿 CSV에는 romaji_ko 열 자체를 두지 않음(build가 생성).
- **content_key**: 독해 `jlpt.n5.reading.####`, 청해 `jlpt.n5.listening.####` (문법 `jlpt.n5.grammar.####`와 동형).
  ⚠️ **규격 4.5/4.4 JSON 예시는 `read`/`listen` 약어**를 썼다(`jlpt.n3.read.0001`). 본 방법론은 지시대로 `reading`/`listening` **정식어**를 쓴다 — **도다이가 규격과 정합 확정 필요**(11장 판단대기 ⑥).

## 7. 데이터 스키마 제안

### 7.1 파일럿(flat CSV) ↔ 프로덕션(JSON)의 관계
- **파일럿은 제작·검토 편의를 위한 평평한 CSV**다(한 행 = 지문/대본 + 문항 1). 사람이 스프레드시트로 훑고 대표님이 QA하기 좋다.
- **프로덕션 임포트는 규격 4.5/4.4/4.6의 JSON**이다 — 독해는 지문 1:문장 N(문장탭), 청해는 대본 1:발화 N(화자분리)이라 CSV 한 행에 안 들어간다.
- build 기계가 **flat CSV → 프로덕션 JSON**으로 변환한다(문장 분리 `。？！`, 화자 분리 `A:/B:`).

### 7.2 독해 스키마 (파일럿 CSV 12열)
```
content_key,level_code,genre,passage_ja,passage_ko,question,choice1,choice2,choice3,choice4,answer,explanation_ko
```
| 컬럼 | 규칙 |
|---|---|
| `genre` | 日記 / 案内(정보검색) / メモ / 手紙 등 지문 장르 |
| `passage_ja` | 브래킷 루비 포함. **≤급수 어휘·문법**. 문장은 `。？！`로 분리(build가 문장탭용 seq 부여) |
| `passage_ko` | 한글 해석(문장 단위 분리는 build가 `passage_ja` seq에 맞춰 매핑) |
| `question`/`choiceN`/`answer` | 객관식. `answer`=정답 choice 번호(1~4). N5는 3~4지선다 |
| `explanation_ko` | `explanation_axis=grammar`(규격 4.6) — "본문 어디에 근거가 있나" |
> 프로덕션 매핑: passage→`reading_texts`, 문장→`reading_sentences`(ja+ruby+romaji_ko+ko), 문항→`questions`(target_type=reading), 선택지→`question_choices`.

### 7.3 청해 스키마 (파일럿 CSV 11열)
```
content_key,level_code,type,script_ja,script_ko,question,choice1,choice2,choice3,choice4,answer
```
| 컬럼 | 규칙 |
|---|---|
| `type` | 課題理解 / ポイント理解 / 発話表現 / 即時応答 |
| `script_ja` | **화자 `A:`/`B:` 구분** + 브래킷 루비. 간투사·망설임은 **`……。`로 표기**(규격 4.4.1 — TTS가 「에-토」로 읽지 않게). 한 행이므로 발화는 `「」`로 묶어 인라인 |
| `script_ko` | 화자 구분 한글 해석 |
| `question`/`choiceN`/`answer` | 객관식. 즉시응답은 응답 후보가 곧 선택지 |
> 프로덕션 매핑: script→`listening_items`(+audio_file: **TTS 파일명만** `jlpt.n5.listening.####.m4a`, 음성은 도다이 파이프라인이 생성), 발화→`listening_lines`(seq+speaker+ja+ruby+romaji_ko+ko), voice_preset·speed 기록(규격 4.4·재생성 대비), 문항→`questions`(target_type=listening, audio_file 필수).

## 8. QA 기계(build) 계획 (`build_reading.py`·`build_listening.py` 신설, `build_grammar.py` QA 재사용)
- **루비 검증**: `{}` 벗김 == 원문, 읽기 이어붙임 == 가나(규격 3.1).
- **한글 발음 생성·대조**: `kana_to_ko(ruby)`로 romaji_ko 기계 생성(A안). 1패스 스코프 규칙(규격 3.2.5-1) 준수.
- **급수 초과 어휘 후보**: 지문/대본 형태소 vs ≤급수 vocab 세트 → 초과 후보 리스트(사람 판정).
- **급수 초과 문법 후보**: 패턴 매칭으로 상위 문형 사용 의심 → 후보 보고(사람 판정).
- **문장 길이 경고**: 1문장 60자 초과 시 경고(규격 4.5 — 문장탭이 전체해석 토글로 변질되는 것 방지).
- **문항 정합**: answer가 choice 범위 내, 정답 1개, content_key 유일, 선택지 중복 0.
- **청해 TTS 표기 검사**: 간투사 뒤 `、`만 있으면 경고(→`……。` 권고, 규격 4.4.1). 화자 라벨 `A:/B:` 파싱 가능 여부.
- **필드 내 ASCII 쉼표·줄바꿈 0**(규격 2.2 — 일본어 `、。`·한글 문장은 통과, ASCII `,`만 금지).

## 9. 실행 파이프라인 (단어·문법 파이프라인 재사용)
1. **선행 조건 확인**: 해당 급수 단어·문법이 이미 채워졌는지(재료 세트 존재).
2. **배치 작성**(슈슈, 급수별): 유형별 지문·대본·문항 자작. N5부터.
3. **기계 검수**(build): 8장 전 항목.
4. **대표님 QA**: 지문·대본 자연스러움, 정답 타당성, 해설 정확도(기계가 못 잡는 것).
5. **청해 음성 생성**(도다이): 대본 → TTS(규격 4.4.1 표기 확정 엔진). 파일명 `content_key.m4a`.
6. **DB 임포트 + 공개**(도다이): flat CSV → JSON 변환 → UPSERT → `is_published` 플립.

## 10. 순서·규모 (예상, 확정 아님)
- **N5 → N4 → N3 → N2 → N1**(사용자가 만나는 순서, 단어·문법과 동일).
- 규모는 표준 목록이 없어 **급수별 목표치를 우리가 정한다**(문법의 "전량"과 다름) → 11장 판단대기 ①.
- 파일럿은 N5 독해 3지문·청해 3대본(초기 배치 검증용).

## 11. 🔴 대표님 판단 대기 항목
1. **급수별 지문·대본 수 목표.** 표준 목록이 없어 우리가 정해야 한다. 예: N5 독해 20지문·청해 20대본? (문법 48항목처럼 목표 규모 확정 필요)
2. **청해 TTS 화자 구성.** `A`=남성1·`B`=여성1 식 **화자 풀을 몇 종**으로 고정할지, voice_preset 매핑을 어떻게 표준화할지(도다이 음성 파이프라인과 직결).
3. **독해 지문 장르 범위.** 파일럿은 일기·안내문·메모 3종. 편지·이메일·게시판·시간표 등 어디까지 확장할지.
4. **객관식 선택지 수.** 4지선다 고정 vs 유형별 가변(실제 N5 청해 즉시응답은 3지선다가 많다). 앱 UI 일관성 ↔ 시험 충실도의 트레이드오프.
5. **지문당 문항 수.** 파일럿은 1지문=1문항. 1~2로 열지(정보검색 지문은 2문항이 자연스러움).
6. **content_key 명명 정합.** 방법론은 `reading`/`listening`, 규격 4.5/4.4 JSON 예시는 `read`/`listen`. 도다이가 스키마와 하나로 확정.
7. **발화표현(発話表現) 유형 채택 여부.** 그림 asset이 필요해 제작비가 오른다(규격 4.6 asset_file). MVP에 넣을지, 후속으로 미룰지.
