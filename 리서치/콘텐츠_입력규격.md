## 0. 이 문서가 하는 일

콘텐츠 제작자(사람/외주/AI)가 **무엇을 어떤 칸에 채워야 하는지**를 정한다.
목표는 하나다 — **여기서 채운 파일이 손을 거의 안 대고 `스키마_설계.md` ② 콘텐츠 마스터에 그대로 들어갈 것.**

> ⭐ 이 규격이 늦으면 손해가 아니라 **재작업**이다. 포맷을 정하지 않고 2,250건을 만들면 2,250건을 다시 만진다.
> 그래서 100건 파일럿을 먼저 돌렸고, **파일럿에서 드러난 결함을 이 문서에 이미 반영**했다(5장).

## 1. 🔴 저작권 — 채우기 전에 반드시 읽을 것

### 1.1 원칙

| | 내용 |
|---|---|
| **금지** | 시중 교재·학원 자료(시원스쿨·해커스·다락원·한권으로끝내기 등)가 **고른 목록 · 배열한 순서 · 쓴 예문 · 쓴 해설**을 가져오는 것 |
| **허용** | 공개 원천(`jlpt.jp` 공식 샘플, 국제교류기금 자료, 라이선스가 명시된 공개 데이터셋) + **우리가 직접 쓴 뜻·예문·해설** |

**왜 단어 하나는 괜찮고 목록은 안 되는가.**
단어 자체(`選ぶ`)는 저작물이 아니다. 그러나 **"N3에 어떤 단어를 골라 어떤 순서로 배열했는가"는 편집저작물로 보호**된다.
교재의 단어장을 그대로 옮기면 단어를 베낀 게 아니라 **편집을 베낀 것**이 된다. 모의고사 문항·해설은 더 명백한 어문저작물이다.

### 1.2 그래서 모든 행에 출처를 적는다

전 콘텐츠 CSV에 `source` 컬럼이 **필수**다. 빈칸이면 임포트 거절.

| `source` 값 | 뜻 | 안전도 |
|---|---|---|
| `own` | 우리가 직접 작성 (뜻·예문·해설은 원칙적으로 전부 여기) | ✅ |
| `jlpt_official` | jlpt.jp 공식 샘플에서 **유형만** 참고 | ✅ (원문 복제 금지) |
| `aozora:{작품ID}` | 青空文庫 (저작권 만료) | ✅ |
| `tanos_ccby` | tanos.co.uk (Jonathan Waller) 데이터를 **값으로 가져다 쓴** 경우 | ✅ CC BY (7.3-1) — 단 **현재 어느 행에도 쓰지 않는다**, 아래 참조 |
| `ref_only:{출처}` | 존재 확인용으로만 봤고 **값은 직접 씀** | ✅ |
| `ref_only:jfs_cando_b1+corpus_freq` | 🆕 **N3 이상 전용.** ①JF Can-do B1로 범위를 자르고 ②공개 코퍼스 빈도로 순위를 매겨 **고르기만** 했다. 뜻·예문은 전부 자작 | ✅ |

> 🆕 **왜 N3부터 `source` 값이 하나로 통일되는가** (2026-07-23 N3 400건 작업 중 확정)
> N5·N4는 교재가 한 권씩 특정돼 `ref_only:jf_irodori_a2` 처럼 **어느 책을 봤는지**가 출처였다.
> N3부터는 교재가 없고 **방법론이 출처**다(7.3-2). 400행 전부가 같은 방법으로 뽑혔으므로
> `source`는 하나면 되고, **행마다 다른 것은 `note`에 적는다** — 어느 Can-do가 이 단어를 불렀는지,
> 코퍼스에서 몇 위인지. `source`만 보면 "어떻게 골랐나"에는 답할 수 있지만
> **"왜 하필 이 단어인가"에는 답할 수 없다.** 그래서 note 쪽이 본체다.

#### 1.2-1 🔴 Tanos는 `source`가 아니라 `note`에 적는다 (2026-07-23 N4 400건 작업 중 확정)

라이선스가 풀렸다고 해서(7.3-1) Tanos를 `source`에 적으면 안 된다. **적는 자리가 뜻을 바꾸기 때문이다.**

| 자리 | 읽히는 뜻 |
|---|---|
| `source = tanos_ccby` | *"이 행의 값을 Tanos에서 가져왔다"* → 2,250건 중 절반에 이게 찍히면 **"우리는 Tanos 목록을 옮긴 앱"** 이 된다 |
| `note = Tanos교차: N4 일치` | *"우리가 고른 뒤 Tanos로 급수를 대조했다"* → 선정은 우리 것, Tanos는 검증 도구 |

- 어휘 **선정의 주 원천은 국제교류기금 교재 축**(`ref_only:jf_*`)으로 고정한다. 교재는 *"실제로 가르치는 순서"* 를 담아 학습 앱에 맞고, Tanos는 순서를 담지 않는다.
- **`note`의 Tanos 판정은 사람이 적지 않는다.** 참조본과 대조해 **기계가 찍는다**. 사람이 적으면 그 값도 검수 대상이 되고, 검증하려고 만든 것이 검증 대상이 되면 의미가 없다.
- 판정 태그 5종: `N4 일치` / `N5 분류 — …흡수` / `목록밖(N3+ 추정) — 교재축 우선` / `미확인(…)` / `대조제외(조수사·접미)`
- ⚠️ **`미확인`을 `일치`로 반올림하지 않는다.** 참조본(.mem)은 Mnemosyne 바이너리라 추출이 완전하지 않다. 못 본 것은 못 봤다고 적는다.

> 🔴 **`source`를 나중에 채우면 못 채운다.** 며칠 지나면 그 단어를 어디서 봤는지 아무도 기억 못 한다.
> 이건 형식주의가 아니라, 문제가 생겼을 때 **"이 2,250건 중 어느 것을 지워야 하나"에 답할 수 있게 하는 유일한 수단**이다.

### 1.3 검수 상태 컬럼도 필수

`verify` 컬럼: `draft`(초안) / `team`(팀 교차검증 완료) / `native`(일본인 감수 완료)
- **비즈니스**: 🔄 **2026-07-23 정정** — *"`native` 없이는 출시 금지"* 는 **취소**되었다(PRD **4.2.5-1**).
  → **입문·초급·중급은 `team`으로 출시 가능**하다. 국제교류기금 교재에 실려 있어 **대조 검증이 되기 때문**이다(N5 단어에 쓴 방법과 동일).
  → **고급(접대·교섭)만 `native` 필요**하며, 그때까지는 출시를 막는 대신 **`is_published=false` 로 아예 노출하지 않는다**(PRD 4.2.5-2).
  ⚠️ 경어가 틀리면 오류가 아니라 **실례**라는 사실은 그대로다. 달라진 것은 *"어디까지 우리가 검증할 수 있는가"* 의 선이다.
- JLPT 단어는 `team`까지로 출시 가능, 단 `native`를 출시 후 순차 적용

## 2. 파일 포맷

### 2.1 무엇을 CSV로, 무엇을 JSON으로

| 콘텐츠 | 포맷 | 이유 |
|---|---|---|
| 단어 · 문법 · 표현 · 청해 | **CSV** | 1행 = 1레코드로 딱 떨어진다. 제작자가 **스프레드시트로 작업**할 수 있어야 하고, diff가 사람 눈에 보인다 |
| 지문(reading) | **JSON** | 지문 1건 안에 문장이 N개 있는 **1:N 중첩**이라 CSV 한 행에 안 들어간다 |
| 문항(question) | **JSON** | 선택지가 N개 있고 개수가 유형마다 다르다 |

> **왜 전부 JSON으로 통일하지 않는가**: 콘텐츠를 채우는 사람은 개발자가 아니다. 2,250줄을 JSON으로 손으로 쓰면 반드시 쉼표·따옴표에서 깨진다.
> **왜 전부 CSV로 통일하지 않는가**: 선택지 4개를 `choice1,choice2,choice3,choice4`로 펼치면 선택지 5개짜리 유형이 나오는 순간 컬럼을 늘려야 한다.
> → **평평한 것은 CSV, 중첩된 것은 JSON.** 경계가 명확해서 헷갈리지 않는다.

### 2.2 CSV 작성 규칙 (전 코스 공통)

| 항목 | 규칙 | 이유 |
|---|---|---|
| 인코딩 | **UTF-8 (BOM 포함)** | BOM이 없으면 **한국어 Windows Excel에서 전부 깨져 보인다.** 임포터가 BOM을 벗기게 한다 |
| 줄바꿈 | `LF` | |
| 구분자 | `,` | |
| **필드 안 쉼표** | **금지.** 여러 값은 `;`로 구분 | 따옴표 이스케이프를 제작자에게 요구하면 반드시 깨진다. "쉼표 대신 세미콜론"이 규칙 하나로 끝난다 |
| 필드 안 줄바꿈 | **금지** | 상동 |
| 빈 값 | `-` (하이픈 1자) | 진짜 빈칸인지 안 채운 건지 구분이 안 된다. `-`는 "해당 없음"의 명시 |
| 첫 행 | 헤더 필수 | |
| 파일명 | `{코스}_{급수}_{종류}_{연번}.csv` 예: `N3_단어_파일럿_100.csv` | |

### 2.3 JSON 작성 규칙

- UTF-8 (BOM 없음), 최상위는 **배열**, 들여쓰기 2칸
- 키는 `snake_case`, 스키마 컬럼명과 **동일하게**

## 3. 🔴 표기 규칙 (이 장이 이 문서의 본체다)

### 3.1 후리가나 — 좌표를 담아야 한다

**문제**: `reading` 컬럼에 `おてつだい`만 있으면, 렌더러는 `お手伝い`의 **어느 글자에 어떤 루비**를 붙일지 모른다.
스키마도 이미 "**루비 좌표 포함 JSON**"이라고 못 박았다(스키마_설계 `reading_sentences.reading`).

**해결**: 제작자는 좌표를 손으로 쓰지 않는다. **브래킷 표기**로 쓰고 임포터가 좌표로 변환한다.

#### 브래킷 표기법

```
{표기|읽기}                     ← 읽기가 1개면 표기 전체에 붙는 그룹 루비
{표기|읽기1|읽기2|...}          ← 읽기 수 = 표기 글자 수면 글자별 모노 루비
```

| 예 | 뜻 | 결과 |
|---|---|---|
| `{食|た}べる` | 送り仮名 | 食에 「た」, べる는 루비 없음 |
| `{日本語|に|ほん|ご}` | 글자별 | 日→に, 本→ほん, 語→ご |
| `{昨日|きのう}` | 熟字訓 | 昨日 전체에 「きのう」 |
| `{発|はっ}{表|ぴょう}` | 촉음 포함 | 発→はっ, 表→ぴょう |
| `{素晴|すば}らしい` | 부분 그룹 | 素晴 전체에 「すば」 |

**변환 규칙 (임포터)**
1. `{}` 안을 `|`로 자른다. 첫 조각 = 표기, 나머지 = 읽기.
2. 읽기 개수 == 표기 **글자 수**  → 글자별로 하나씩 붙인다.
3. 읽기 개수 == 1 → 표기 전체에 하나로 붙인다(그룹 루비).
4. 그 외 → **에러**. 조용히 넘어가지 않는다.

**산출 JSON** (스키마의 `reading` 컬럼에 들어갈 값)
```json
{
  "base": "お手伝い",
  "ruby": [ { "s": 1, "e": 2, "rt": "て" },
            { "s": 2, "e": 3, "rt": "つだ" } ]
}
```
- `s` / `e` = **코드포인트 기준** 시작·끝 인덱스(0-based, 끝 미포함)
- 🔴 **UTF-16 인덱스가 아니다.** JS는 문자열을 UTF-16으로 세기 때문에 서로게이트 페어 한자(𠮟 등)에서 어긋난다.
  → 무스부에게: 렌더러는 `Array.from(base)`로 쪼갠 뒤 인덱싱할 것.

**검증**: `{}`를 다 벗긴 결과 == `headword`, 읽기만 이어 붙인 결과 == `reading` 이어야 한다. 둘 다 자동 체크한다.

> ⭐ 브래킷 표기를 **원본으로 보관**한다(CSV의 `ruby` 컬럼). 좌표 JSON은 파생물이다.
> 이유: 좌표를 원본으로 두면 사람이 고칠 수 없다. 오타 하나 고치자고 인덱스를 다시 세게 만들면 안 된다.

### 3.2 한글 발음 — 규칙과 **한계**

#### 3.2.1 먼저, 이 필드의 목적

한글 발음은 **정확한 발음 재현이 아니다.** PRD 8.4가 이미 "빨리 떼야 할 보조바퀴"로 규정했고, 부작용(발음 왜곡)도 명시했다.
따라서 규칙의 목표는 **"가장 비슷하게"가 아니라 "항상 똑같이"** 다.

> **왜 일관성이 정확성보다 우선인가**: 같은 가나가 자리에 따라 다르게 적히면, 초보는 가나↔한글 대응을 세우지 못한다.
> 대응을 못 세우면 한글 발음을 **떼지 못한다.** 뗄 수 없는 보조바퀴는 목적에 정면으로 반한다.

#### 3.2.2 기본 대응표 (⚠️ 국립국어원 외래어표기법과 의도적으로 다름)

> ⚠️ 이 선택의 대가는 3.2.5의 첫 줄에 적어 두었다. 대표님 결정 항목 8장 ①.

#### 3.2.3 촉음 `っ` — 받침으로

| 뒤에 오는 행 | 받침 | 예 |
|---|---|---|
| か행 | **ㄱ** | がっこう → **각**코오 |
| さ·た행 | **ㅅ** | ねっしん → **넷**신 / きって → **킷**테 |
| ぱ행 | **ㅂ** | いっぱい → **입**파이 |
| 어말 | 표기하지 않음 | あっ → 아 |

> 한국어 받침이 실제로 그 위치에서 폐쇄를 만들기 때문에, 촉음은 **한글로 꽤 정확히 표기되는 드문 항목**이다.

#### 3.2.4 발음 `ん` — 뒤 자음에 따라

| 뒤에 오는 것 | 받침 | 예 |
|---|---|---|
| ま·ば·ぱ행 | **ㅁ** | しんぶん → **심**분 / さんぽ → **삼**포 |
| か·が행 | **ㅇ** | てんき → **텡**키 / かんきょう → **캉**쿄오 |
| さ·ざ·た·だ·な·ら행 | **ㄴ** | あんない → **안**나이 |
| 어말 · 모음 · や · わ · は행 앞 | **ㄴ** | にほん → 니혼 |

> 한국어의 자음동화와 자연스럽게 일치해서, **한국인은 규칙을 배우지 않고도 그대로 읽는다.**

#### 3.2.5 장음 — 앞 모음을 반복한다

`とうきょう` → **토오쿄오** (`토우쿄우` ✕, `토-쿄-` ✕)

| 가나 | 표기 |
|---|---|
| おう · おお | 오오 |
| えい · ええ | 에에 |
| うう / いい / ああ | 우우 / 이이 / 아아 |
| 가타카나 `ー` | 앞 음절의 모음 반복 (サービス → 사**아**비스) |

**🔴 장음 판정 범위 = 루비 1개 안에서만.**
```
{東|とう}{京|きょう}   → とう가 한 루비 안 → 장음 → 토오쿄오   ✅
{思|おも}う            → う가 루비 밖     → 장음 아님 → 오모우 ✅
{場|ば}{合|あい}       → ば와 あい는 다른 루비 → 바아이        ✅
```
> 이 규칙이 없으면 `思う`가 '오모오'가 된다. **루비를 먼저 정하게 만든 설계가 여기서 값을 한다** — 형태소 경계를 사람이 따로 판단하지 않아도 된다.
> `ー`(U+30FC)나 `-`를 쓰지 않는 이유: 한글 폰트에 그 글리프가 없으면 두부(□)가 뜬다. 순한글로 유지하면 폰트 리스크가 0이다.

#### 3.2.5-1 🔴 스코프가 규칙마다 다르다 (구현 시 반드시)

파일럿 100건을 기계 변환하다가 나온 것이다. **처음 만든 변환기는 14건이 틀렸고, 원인은 전부 하나였다.**

| 규칙 | 루비 경계를 | 예 |
|---|---|---|
| **장음** | **넘지 않는다** | `{場|ば}{合|あい}` → 바아이 (ばあ를 장음으로 보면 안 됨) |
| **촉음 `っ`** | 🔴 **넘는다** | `{発|はっ}{表|ぴょう}` → **합**표오. `っ`는 루비1의 끝인데 **받침은 루비2의 첫 글자**(ぴ)를 보고 정해진다 |
| **발음 `ん`** | 🔴 **넘는다** | `{準|じゅん}{備|び}` → **줌**비 / `{天|てん}{気|き}` → **텡**키 |

> 그래서 변환기는 **루비 조각별로 따로 돌리면 안 된다.**
> 가나를 **한 줄로 펴 놓고 글자마다 "루비 안인가" 플래그만 달아서 1패스로 처리**해야 한다.
> 조각별로 돌리면 `발표`가 '하표오', `준비`가 '준비'로 나온다 — 그리고 **조용히 틀린다.**

#### 3.2.5-2 🔴 순가나 복합어는 **형태소 경계를 표시할 방법이 없다** (2026-07-23)

3.2.5-1이 *"장음은 조각 경계를 넘지 않는다"* 로 형태소 문제를 풀었는데, **한 군데 구멍이 남아 있었다.**

> **조각 경계는 「루비 브래킷」으로만 생긴다.** 한자가 없는 복합어는 브래킷이 없으니 **경계가 안 보인다.**

| 예 | 잘못 | 옳음 | 이유 |
|---|---|---|---|
| `そのうえ` | 소노**오**에 | **소노우에** | `その` + `うえ(上)` — う는 うえ의 일부지 の의 장음이 아니다 |

**대응**: `WORD_EXCEPTIONS` 에 **브래킷을 넣어 조각을 강제로 나눈다.** 읽기를 표기와 같게 두면 루비는 생기지 않는다.
```python
'そのうえ': 'その{うえ|うえ}',   # の와 う가 다른 조각 → 장음 성립 안 함
```

**🔴 재발 방지 — 순가나 표제어는 반드시 이 검사를 돌린다**
```bash
cd "C:/github/JangSonglee/japanese-study-app/리서치" && python -c "
import csv,io,re,glob
OU=re.compile('[おこそとのほもよろごぞどぼぽきしちにひみりぎじぢびぴ][ぅう]|[えけせてねへめれげぜでべぺ][ぇえ]')
for f in sorted(glob.glob('02_JLPT/*.csv')):
    for x in csv.DictReader(io.open(f,encoding='utf-8-sig')):
        if '{' not in x['ruby'] and OU.search(x['ruby']):
            print(f.split('/')[-1], x['headword'], '->', x['romaji_ko'])"
```
→ 출력된 항목을 **하나씩 눈으로 확인**한다. 대부분은 진짜 장음(`どうぞ`→도오조, `あのう`→아노오)이라 **정상이다.**
**틀린 것만 골라내는 자동 판정은 불가능하다** — 형태소 사전이 필요한 문제라서, 여기서는 **기계가 후보를 좁히고 사람이 판정**한다.

> ⚠️ **1,200건 중 13건이 후보였고 그중 1건이 오류였다.** 자동으로는 못 잡지만, **13건만 보면 되므로 사람이 감당할 수 있다.**

#### 3.2.6 조사 예외

| 가나 | 읽기 | 표기 |
|---|---|---|
| は (조사) | わ | **와** — `{実|じつ}は` → 지츠**와** |
| へ (조사) | え | **에** |
| を | お | **오** |

#### 3.2.6-1 🔴 조사 `は`는 **규칙이 아니라 어휘 목록**으로 잡는다 (2026-07-23 N4 400건 작업 중 확장)

변환기는 「순가나 런 **전체**가 정확히 `は`/`へ`일 때」만 조사로 본다. 그래서 `{実|じつ}は`(런이 `は` 하나)는 통과하지만,
**앞에 다른 가나가 붙은 한 덩어리**는 못 잡고 **조용히 틀린다.**

```
それでは → 소레데하 ✕   (それでわ → 소레데와 가 맞다)
または   → 마타하   ✕   (またわ   → 마타와   가 맞다)
```

**런 안을 스캔해서 `は`를 찾는 방식은 쓸 수 없다.** 그러면 `はは`(母)가 '하와'가 된다.
조사인지 아닌지는 **형태소 정보**이지 표기 정보가 아니다. 표기만 보고 판정할 방법이 원리적으로 없으므로, **어휘 단위 예외가 유일한 해법**이다.

| 어휘 예외 (`kana_to_ko.WORD_EXCEPTIONS`) | → |
|---|---|
| `こんにちは` `こんばんは` | `〜わ` |
| `それでは` `では` `または` | `〜わ` |

> ⭐ 새 어휘를 넣을 때 **가나 안에 조사 `は`가 섞여 있으면 이 목록에 먼저 추가**한다. 변환기를 고치려 들면 안 된다.
> → 무스부/도다이: TS 포팅 시 이 목록을 **데이터로** 들고 가라. 코드에 하드코딩하면 다음 급수에서 또 고친다.

#### 3.2.7 🔴 한글로 적을 수 없는 것 (반드시 명시하고 살아간다)

| 항목 | 우리 표기 | 실제 | 무엇이 틀리는가 |
|---|---|---|---|
| `つ` | 츠 | [tsɯ] | 한국어에 [ts]가 없다. '츠'는 [tʃʰ]에 가까워 **명백히 다른 소리** |
| `ざじずぜぞ` | 자지즈제조 | [dz][dʑ] | 한국어 ㅈ는 무성음. **유성 마찰음을 낼 수 없다** |
| `ぢ づ` | 지 즈 | — | `じ`/`ず`와 **구분이 사라진다** (일본어에서도 거의 합류했으므로 실해는 작다) |
| `ん` | ㄴ/ㅁ/ㅇ | [ɴ][n][m][ŋ][Ṽ] | 어말 `ん`은 구개수 비음. **한글에 없다** |
| `ふ` | 후 | [ɸɯ] | 양순 마찰음. '후'는 성문음 |
| `う` | 우 | [ɯ] | 입술을 둥글게 하지 않는 소리. '우'는 원순 |
| **어두 청음** | 카 타 파 | 무기 무성음 | 한국어 격음보다 훨씬 약하다. **3.2.2 선택의 대가** |
| **고저 악센트** | **표기 없음** | あめ(비)≠あめ(사탕) | 한글로는 원리적으로 불가 |

> 🔴 **악센트가 표기 불가라는 사실이 결론을 만든다.** 한글 발음만으로는 절대 도달할 수 없는 층이 있으므로,
> **발음의 진짜 담당은 음성 파일**이고 한글 발음은 초반 몇 주의 진입 보조일 뿐이다.
> 앱이 이 토글을 끄도록 유도하는 PRD 8.4의 설계는 **음성학적으로도 옳다.** 이 표를 앱의 설정 화면 도움말에도 노출할 것을 권한다.

## 4. 콘텐츠별 입력 규격

### 4.0 전 콘텐츠 공통 컬럼

| 컬럼 | 필수 | 설명 |
|---|---|---|
| `content_key` | ✅ | **사람이 읽는 안정 키.** `{코스}.{급수}.{종류}.{4자리}` 예: `jlpt.n3.vocab.0001` |
| `level_code` | ✅ | `course_levels.code` (`N3`, `restaurant`, `basic` …). uuid가 아니라 코드로 받아 임포터가 매핑 |
| `source` | ✅ | 1.2 참조 |
| `verify` | ✅ | `draft` / `team` / `native` |
| `note` | | 제작자 메모. 임포트되지 않음 |

> 🔴 **`content_key`가 왜 필수인가 (파일럿 최대 수확).**
> 스키마의 PK는 uuid인데 **콘텐츠 제작자는 uuid를 만들 수 없다.** 이것 때문에 세 가지가 전부 막힌다.
> ① **음성 파일명을 정할 수 없다** — uuid는 임포트 후에 생기는데 음성은 그 전에 만든다.
> ② **재임포트가 불가능하다** — 오타 하나 고쳐 다시 넣을 때마다 중복 행이 생긴다. 자연키가 있어야 UPSERT가 된다.
> ③ **오류를 보고할 수 없다** — "3f2a-…-9c1 행이 이상함"은 사람이 못 찾는다.
> → 스키마 변경 요청 5장 ①.

#### 4.4.1 🔴 간투사·망설임은 **글자가 아니라 「멈춤」으로 쓴다** (2026-07-23 실측 확정)

**발견**: TTS에 `えーと、` 라고 쓰면 **망설임을 연기하지 않고 「에-토」라고 글자 그대로** 읽는다. 대화가 통째로 어색해진다.
**해결**: 뒤에 **삼점 리더 + 마침표(`……。`)** 를 붙인다. 실제 침묵이 생기면서 *"생각하는 중"* 으로 들린다.

| | 표기 | 결과 |
|---|---|---|
| ❌ | `えーと、まだです。` | 「에-토」로 딱딱하게 읽음 |
| ✅ | `えーと……。まだです。` | **자연스러운 망설임** ← 채택 |
| △ | `……まだです。`(간투사 제거) | 자연스럽지만 망설임의 뉘앙스가 사라짐 |
| △ | 속도 −18% | 개선 폭이 작고 전체가 늘어짐 |

**규칙**
1. **간투사**(`えーと` `あのう` `うーん`) 뒤에는 **`、`가 아니라 `……。`**
2. **말끝 흐림**도 동일: `つもりですが……。`
3. ⚠️ **남발 금지** — 모든 줄에 넣으면 대화가 통째로 느려진다. **실제로 망설이는 자리에만.**
4. ⚠️ 이 값은 **Azure Neural 계열에서 확인**했다. **엔진을 바꾸면 다시 들어보고 확정**할 것(사양서 5.1).

> **왜 이게 통하는가**: 망설임의 본질은 **소리가 아니라 침묵**이다. TTS는 구두점에서 멈추는데 `、`는 짧고 `。`는 길다. `……。` 조합이 "생각하는 길이"를 만든다.
> 🔴 **이 규칙 하나로 성우 녹음이 불필요해졌다** — `청해_음성_제작_검토.md` 참조.

### 4.5 지문 `reading_texts` + `reading_sentences` — JSON

🔴 **통짜 텍스트 금지.** 반드시 문장 단위로 쪼개고, 문장마다 4개를 각각 채운다.
(스키마_설계 0장 3번 — 해석이 토글이 아니라 **문장 탭**이라, 통으로 저장하면 기능 자체가 불가능하다)

```json
[
  {
    "content_key": "jlpt.n3.read.0001",
    "level_code": "N3",
    "group_key": "-",
    "title": "図書館の使い方",
    "est_minutes": 3,
    "has_memo": false,
    "published_at": "-",
    "source": "own",
    "verify": "draft",
    "sentences": [
      {
        "seq": 1,
        "ja": "{駅|えき}の{近|ちか}くに{新|あたら}しい{図書館|としょかん}ができました。",
        "romaji_ko": "에키노 치카쿠니 아타라시이 토쇼칸가 데키마시타",
        "ko": "역 근처에 새 도서관이 생겼습니다."
      },
      { "seq": 2, "ja": "…", "romaji_ko": "…", "ko": "…" }
    ]
  }
]
```

| 필드 | 대응 | 주의 |
|---|---|---|
| `ja` | `reading_sentences.ja` + `reading` | 브래킷을 벗기면 `ja`, 좌표로 바꾸면 `reading`. **한 필드로 둘 다 만든다** |
| `ko` | `reading_sentences.ko` | 🔴 **문장 단위.** 하단 `전체 해석 보기`는 `ko`를 seq 순으로 이어 붙이면 되므로 따로 쓰지 않는다 |
| `group_key` | | 같은 이야기의 3단 난이도를 묶는 키(전래동화·뉴스). 단독이면 `-` |

**문장 분리 기준**: `。` `？` `！` 뒤에서 자른다. 단 「」 안의 인용은 자르지 않는다.
> **왜 문장이 너무 길면 안 되나**: 문장 탭은 "막힌 한 문장만 여는" 장치다. 한 문장이 4줄이면 사실상 전체 해석 토글이 되어 우리가 기각한 방식으로 되돌아간다. **1문장 60자 초과 시 검수 경고.**

### 4.6 문항 `questions` + `question_choices` — JSON

```json
[
  {
    "content_key": "jlpt.n3.q.0001",
    "level_code": "N3",
    "track_code": "vocab",
    "question_type": "mcq",
    "target_type": "vocab",
    "target_key": "jlpt.n3.vocab.0001",
    "stem_ja": "この{中|なか}から{一|ひと}つ{選|えら}んでください。",
    "stem_ko": "-",
    "audio_file": "-",
    "asset_file": "-",
    "explanation": "「選ぶ」는 여러 개 중에서 고른다는 뜻입니다.",
    "explanation_axis": "grammar",
    "is_auto_generated": false,
    "source": "own",
    "verify": "draft",
    "choices": [
      { "seq": 1, "text": "고르다", "is_correct": true,  "wrong_reason": "-" },
      { "seq": 2, "text": "나르다", "is_correct": false, "wrong_reason": "「運ぶ」의 뜻입니다." }
    ]
  }
]
```

**`question_type` 6종**
| 값 | 화면 | 필수 필드 |
|---|---|---|
| `mcq` | 객관식 | `choices` 2개 이상, 정답 1개 |
| `dictation` | 받아쓰기 | 정답은 `choices` 1개(is_correct=true)에 **かな로** — 앱 내장 가나 키보드 입력이라 한자 정답 금지 |
| `matching` | 짝맞추기 | `choices`를 짝 단위로. `pair_key` 필드 추가 |
| `listening` | 청해 | `audio_file` 필수 |
| `ordering` | 순서배열 | `choices.seq`가 **정답 순서** |
| `speaking` | 스피킹 | 정오 판정 없음 → `choices` 없음, `wrong_reason` 없음, **오답노트에 담지 않음**(JLPT 검토 ⑤) |

**`explanation_axis`**
| 값 | 코스 | 해설이 답해야 할 질문 |
|---|---|---|
| `grammar` | **JLPT** | "문법적으로 왜 이게 맞는가" — 문형 / 독해 근거 위치 / 어휘 음독·훈독 구분 |
| `appropriateness` | **여행 · 비즈니스** | "이 상황에서 적절한가" — 정중도·상대·장면. *"틀린 문장은 아니지만 손윗사람에겐 실례입니다"* |

> 🔴 **축을 헷갈리면 해설을 통째로 다시 쓴다.** 비즈니스 문항에 문법 해설을 달면 "왜 이게 실례인지"를 아무도 설명하지 않게 된다.

**3단 해설 매핑** (JLPT 검토 ⑥-1)
| 단 | 어디에 |
|---|---|
| ① 정답이 무엇인가 | `choices.is_correct` |
| ② 왜 정답인가 | `questions.explanation` |
| ③ 오답은 왜 틀렸는가 | `choices.wrong_reason` (**선택지별**, JLPT만 채움) |
> ✅ 3단 구조는 현재 스키마로 **추가 컬럼 없이 표현된다.** 다만 ③은 비즈니스·여행에서 **축소**하기로 했으므로(BJT 검토), 그 코스는 `-`로 둔다.

**`asset_file`** — 비즈니스 `総合聴読解`용 자료 이미지(견적서·결산표·그래프·이메일 화면). PRD 4.2.4 / 스키마 `questions.asset_url`.
> ⚠️ **이 한 컬럼이 제작비를 올린다.** 이미지를 만들어야 하고, 숫자가 들어간 서류는 일본인 감수 대상이다.

### 7.1 🔴 결론: 공식 근거는 **없다**

| 확인된 사실 | 출처 |
|---|---|
| **주최측은 급수별 어휘 목록·어휘 수를 공개하지 않는다.** 2010년 개편 때 "『出題基準』의 공개는 반드시 적절하지는 않다고 판단했다"고 공식 FAQ에 명시 | jlpt.jp 공식 FAQ 4-2 |
| 공식 급수 설명(levelsummary)에도 **어휘 수는 한 줄도 없다.** N3는 "N1·N2와 N4·N5를 잇는 **다리(橋渡し)**"라고만 기술 | jlpt.jp 공식 |
| 공식 수치가 존재했던 유일한 문서는 **구시험(2009년까지) 『日本語能力試験出題基準 改訂版』**(国際交流基金·日本国際教育協会, 凡人社, 2002) — **인쇄 단행본이며 온라인 미공개** | CiNii / NDL 서지 |

→ **N1~N5 각각의 목표 어휘 수는, 공식적으로 존재한 적이 없다.**

### 7.2 시중 수치(800 / 1,500 / 3,750 / 6,000 / 10,000)의 정체

가장 널리 인용되는 이 수치는 **Jonathan Waller(tanos.co.uk)의 추정치**이며, 본인이 명시적으로 추정임을 밝히고 있다.
- tanos N3 페이지: "There's no **official** JLPT N3 vocabulary, kanji or grammar list" — N3는 다른 급에서 **추정(estimated)**해야 한다고 직접 기술
- 파생 데이터셋(yomitan-jlpt-vocab)도 "Official vocabulary lists do not exist for the JLPT, so these lists are essentially an **educated guess**"라고 명기

**그리고 N3 = 3,750은 산술 보간이다.** 구시험 3급 1,500과 2급 6,000의 **정확한 중간값**이다.
```
(1,500 + 6,000) ÷ 2 = 3,750
```

### 7.3 현재 프로젝트의 `2,250`은 어디서 왔는가

추적된다. **누계 3,750 − N4 누계 1,500 = 2,250** — 즉 **Tanos 누계의 차분(신규 어휘)** 이다.
누계로 전 급수를 펼치면 이렇게 된다.

| 급수 | 누계(Tanos 추정) | **신규 = 수집형 분모 후보** | 근거 강도 |
|---|---|---|---|
| N5 | 800 | **800** | 구시험 4급 공식 수치와 동일 (2차 인용) |
| N4 | 1,500 | **700** | 구시험 3급 공식 수치와 동일 (2차 인용) |
| N3 | 3,750 | **2,250** | 🔴 **보간값의 차분 — 근거 가장 약함** |
| N2 | 6,000 | **2,250** | 구시험 2급 공식 수치와 동일 (2차 인용) |
| N1 | 10,000 | **4,000** | 구시험 1급 공식 수치와 동일 (2차 인용) |

> ⚠️ 위 표는 **"근거 있는 수치"가 아니라 "출처가 추적되는 수치"** 다. 둘은 다르다.
> N5·N4·N2·N1은 *구시험 공식값의 2차 인용*이고, **N3만은 아무 실측도 없는 순수 보간**이다.
> 하필 우리의 우선 급수가 N3다.

| 동사 어미 う | 장음으로 오판되는지 | 迷う · 通う · 払う |

| 조사 は | 발음 예외 | 実は(지츠와) |
| 가타카나 `ー` | 장음 처리 | サービス · インターネット |

### 9.2 파일럿이 실제로 바꾼 것

| 발견 | 규격 반영 |
|---|---|

**🔴 N1 착수 전 결론낼 것 — 분야축(genre-skew) 구체화 초안.**
N1은 ①축(Can-do)이 없고 ②축(빈도)도 죽는다(정의상 드문 말). 대신 **장르 편중도**를 신호로 쓴다:
- 신문(사설·경제·정치) · 학술(논문 초록) · 문학(소설·평론) 세 장르 코퍼스에서 각각의 상대빈도를 재고,
  **특정 장르에서만 튀는 정도**(예: 학술에서만 상위인 「考察·仮説·検証」)를 선정 신호로 삼는다.
- 원천 후보: wordfreq는 장르 분리가 안 되므로, **장르가 태그된 공개 코퍼스**가 필요하다(青空文庫=문학, 신문 사설 아카이브 등).
  라이선스는 N3에서 세운 원칙(상용 회색지대 배제) 그대로 적용 — 착수 전 원천 확보 가능성부터 검증해야 한다.
- ①축 공백은 **JLPT N1 공식 「할 수 있는 일」 기술**(jlpt.jp levelsummary, C1 상당)로 최소 범위만 잡고, 나머지는 분야축이 채운다.
